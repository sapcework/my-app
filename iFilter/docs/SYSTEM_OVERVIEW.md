## 1. このソフトは何をするのか

Windows パソコン全体を対象にした、子供向けのインターネットフィルターです。
ブラウザの拡張機能ではありません。

### なぜ拡張機能ではないのか

ブラウザ拡張には 2 つの弱点があります。

- **ブラウザごとに作る必要がある** — Chrome / Edge / Firefox / Brave でそれぞれ別実装
- **消されたら終わり** — 子供が拡張を無効にすれば効かなくなる

そこで、パソコンがインターネットに繋がる**もっと手前の場所**で止めることにしました。
ここなら、どのブラウザからでも、ブラウザ以外のアプリからでも同じように効きます。

### どこで止めているのか

パソコンがサイトを開くとき、実は 2 段階の動きをしています。

```
  ① 「example.com の住所（IP アドレス）を教えて」  →  DNS サーバー
     「93.184.216.34 です」                        ←

  ② 93.184.216.34 へ接続してページを取得
```

**iFilter は ① の役をひきうけます。** 見せてよいサイトなら本当の住所を教え、
見せられないサイトなら「そんなサイトはありません」と答えます。
住所が分からなければ ② に進めないので、通信そのものが始まりません。

この方式の利点は、**通信の中身を一切見なくてよい**ことです。
何を読んだか、何を書いたかは iFilter には分かりようがありません。
プライバシー方針（後述）が「頑張って守っている」のではなく、
**構造上そもそも取得できない**のはこのためです。

## 2. 全体の地図

```
   ┌──────────────────────────────────────────────┐
   │  ネットワーク層（Windows 固有）              │
   │                                              │
   │   DNS プロキシ      WFP（IP 遮断）           │
   │   windows/dns       windows/wfp              │
   └────────────────┬─────────────────────────────┘
                    │  「example.com はどうする？」
                    ▼
   ┌──────────────────────────────────────────────┐
   │  Core 層（どの OS でも動く。I/O を持たない） │
   │                                              │
   │   filter-core  ←  storage（SQLite）          │
   │       │                                      │
   │       ▼                                      │
   │   policy-engine  ←  domain-model             │
   └────────────────┬─────────────────────────────┘
                    │  「遮断。理由はこう」
                    ▼
   ┌──────────────────────────────────────────────┐
   │  ネットワーク層が結果を実現する              │
   │   DNS: 「見つかりません」と答える            │
   │   WFP: 接続を拒否する                        │
   └──────────────────────────────────────────────┘
```

上の層と下の層で**役割がはっきり分かれている**のがこのシステムの要点です。
次の章で、なぜそこまで厳しく分けるのかを説明します。

## 3. いちばん大事な決まり

### 判定するのは Core 層だけ

**ネットワーク層は「どうするか」を絶対に決めません。** Core 層に問い合わせて、
返ってきた答えを実現するだけです。

```rust
// 悪い例: ネットワーク層が自分で判断している
if category == "adult" {
    return Action::Block;      // ← これを書いてはいけない
}

// 良い例: Core に聞いて、結果を実現するだけ
let verdict = core.decide(&request)?;
```

なぜここまで厳しくするのか。判定を 2 か所に書くと、**必ずずれるから**です。
片方だけ直して、もう片方を忘れる。すると
「画面では許可になっているのに実際は繋がらない」という、
原因の分かりにくい不具合が生まれます。
子供の安全に関わる判断を二重管理するのは危険です。

将来 Android 版を作るときも、判定部分をそのまま持っていけます。

### Core 層は外の世界に触らない

`policy-engine` と `domain-model` は、次のものに一切触りません。

- ファイル
- データベース
- ネットワーク
- OS の機能
- **現在時刻**

最後の「現在時刻」は意外に思うかもしれません。時刻は関数の引数として**外から渡します**。

```rust
// 時計を読まない。時刻は呼び出し側が渡す
pub fn evaluate(request: &Request, ctx: &PolicyContext) -> Verdict
//                        ↑ この中に at: OffsetDateTime が入っている
```

理由は 2 つあります。

- **テストが書きやすい** — 「夜 10 時ならどうなるか」を、実際に夜まで待たずに試せる
- **結果が毎回同じになる** — 同じ入力なら必ず同じ答えになり、原因を追いやすい

この制約は機械的に検査していて、破ると CI が落ちます。

## 4. 部品の一覧

Rust の「クレート」（crate）という単位で分かれています。
クレートは、ひとまとまりのコードの箱だと考えてください。

| クレート | 規模 | 役割 |
| --- | --- | --- |
| `domain-model` | 約 2,260 行 | 型の定義。ドメイン名・カテゴリ・プロファイル・同梱データ |
| `policy-engine` | 約 490 行 | 判定の本体。9 段階の順序 |
| `storage` | 約 1,060 行 | SQLite への保存と読み出し |
| `filter-core` | 約 350 行 | 上 3 つをまとめ、**判定の唯一の入口**になる |
| `ifilter-cli` | 約 720 行 | コマンドラインの道具。動作確認に使う |
| `windows/dns` | 約 920 行 | DNS プロキシ。問い合わせを受けて答える |
| `windows/service` | 約 1,700 行 | Windows サービスとして常駐させる |
| `windows/wfp` | 約 290 行 | IP アドレスでの遮断 |
| `apps/windows-ui` | — | 保護者向けの画面（Rust + React） |

**判定の中心（`domain-model` + `policy-engine`）が全体の 3 割程度**で、
残りは「それをどう届けるか」の配線です。この比率は意図的なものです。

### 依存の向き

```
   ifilter-cli ─┐
   windows/dns ─┼─→ filter-core ─→ policy-engine ─→ domain-model
   windows/ui  ─┘        │
                         └────────→ storage ──────→ domain-model
```

**矢印は必ず一方向**です。`domain-model` は何にも依存せず、
`policy-engine` は `domain-model` だけに依存します。
逆向きの矢印（Core がネットワーク層を呼ぶ）は存在しません。

## 5. 1 回の問い合わせを追いかける

子供が `example.com` を開こうとしたとき、何が起きるかを順に見ます。

### ① DNS プロキシが問い合わせを受け取る

`windows/dns` が UDP の 53 番ポートで待っています。
ブラウザからの問い合わせが、生のバイト列として届きます。

```
[0x12 0x34 0x01 0x00 ... 'example' 'com' ... ]
```

ここから**サイト名だけ**を取り出します。DNS の細かい仕様は極力扱いません。
必要なのは「どのサイトを聞かれたか」だけだからです。

### ② Core 層に問い合わせる

```rust
let verdict = core.decide(&domain, now, RequestSource::Dns);
```

`RequestSource::Dns` は「どこから来た問い合わせか」の記録です。
**この値を判定に使ってはいけません。** 記録専用です。
使ってしまうと「DNS 経由なら通すが UI からは通さない」といった
一貫性のない状態が生まれます。

### ③ 判定する

次の章で詳しく説明します。結果はこういう形で返ります。

```rust
Verdict {
    decision: Block,              // 遮断
    reason: RiskCeiling,          // 危険度の上限を超えた
    matched_rule: "beginner.risk.high",
    trace: [ ... ],               // 9 段階のどこで決まったかの記録
}
```

`trace` があるのがこのシステムの特徴です。
**「なぜ止まったか」を保護者が読める**ことを重視しているためです。

### ④ 結果を実現する

| 判定 | DNS プロキシの動き |
| --- | --- |
| 許可 | 問い合わせを**そのまま**上流の DNS へ転送し、返事もそのまま返す |
| 遮断 | 「そんなサイトはありません」（NXDOMAIN）と答える |
| 要確認 | 遮断と同じ。DNS には「待って」を表す方法がないため |

許可のとき**中身を解析せずそのまま転送する**のがポイントです。
新しい種類の問い合わせが将来増えても、iFilter が壊れることはありません。

### ⑤ 記録する

`access_decisions` テーブルに 1 行足します。保存するのは
**時刻・端末・サイト名・種類・判定・モード・ルール**の 7 項目だけです。

記録に失敗しても、**判定は続けます**。
記録できないことを理由に通信を止めると、
データベースの不調が「インターネットに繋がらない」事故になってしまうからです。

## 6. 判定エンジンの中身

`policy-engine` の `evaluate()` は**純粋な関数**です。
入力が同じなら必ず同じ結果を返し、外の世界に影響を与えません。

### 9 段階を上から順に

**最初に答えが出た段で打ち切ります。** 下の段は評価されません。

| # | 段 | 内容 | 現状 |
| --- | --- | --- | --- |
| 1 | 緊急ブロック | システム定義の停止リスト | 枠だけ（空） |
| 2 | 保護者の拒否 | 拒否リスト | 実装済み |
| 3 | 解除不可カテゴリ | 保護者でも許可できない種類 | `doh` のみ |
| 4 | 保護者の許可 | 許可リスト | 実装済み |
| 5 | 時間帯 | 就寝時間など | 枠だけ（無効） |
| 6 | 危険度の上限 | モードごとの上限を超えるか | 実装済み |
| 7 | 種類ごとのルール | 学習は許可、ゲームは要確認、など | 実装済み |
| 8 | 未知の扱い | 分類が無いサイト | 実装済み |
| 9 | 既定 | どれにも当たらなかった場合 | 実装済み |

### 順序が意味を持つ例

**3 段目が 4 段目より上にある**ことには、実際の意味があります。

`doh`（フィルターを迂回する仕組み）は 3 段目に入っています。
もし 7 段目の「種類ごとのルール」だけで遮断していたら、
保護者が 4 段目の許可リストに入れた瞬間に通ってしまいます。
そして**その 1 件を許可しただけで、他のすべての設定が無効になります**。

画面の「まとめて許可」ボタンは、まさにその操作をしてしまう動線でした。
実際に画面を動かして初めて気づいた問題です（ADR-0009）。

### 複数の種類を持つサイト

1 つのサイトが「動画」と「SNS」の両方に分類されることがあります。
このときは**いちばん厳しい判断が勝ちます**。

```
   遮断  >  要確認  >  許可
```

### 危険度とカテゴリを混ぜない

`DomainRecord.risk_level` は**そのサイト自身**への評価です。
カテゴリの既定危険度を流し込んではいけません。

混ぜると、6 段目（危険度の上限）が 7 段目（種類ごとのルール）を追い越し、
**モードのカテゴリ設定が永久に効かなくなります**。
これは設計中に見つけて直した実際の誤りです。

## 7. ドメイン名の扱い

地味ですが、**ここがいちばんバグを生みやすい**部分です。

### 階層をどこまで遡るか

`www.a.example.co.jp` というサイト名が来たとき、
登録済みの設定を探すために名前を短くしていきます。

```
   www.a.example.co.jp
       a.example.co.jp
         example.co.jp     ← ここで止める
             co.jp         ← ここまで降りてはいけない
                jp
```

`co.jp` まで降りると、**「co.jp を許可」で日本のほぼ全サイトが通ります**。
そこで「登録可能な一番短い名前」（eTLD+1）で打ち切ります。

`co.jp` や `com` のような「その下に誰でも登録できる部分」の一覧は
公開サフィックスリスト（Public Suffix List）として公開されていて、
`psl` というライブラリに埋め込まれています。実行時に取りに行く必要はありません。

### 文字列の後ろ比較をしない

```rust
// 悪い例: notexample.com が example.com にヒットしてしまう
domain.ends_with("example.com")

// 良い例: ラベル（ドットで区切られた単位）の境界で比べる
```

### 大手 CDN という例外

ここで厄介な問題が起きます。`cloudfront.net` や `googleapis.com` などの
大手配信網は、**公開サフィックスリストに載っています**。

つまり `d111abc.cloudfront.net` の「登録可能な一番短い名前」は
**それ自身**であり、`cloudfront.net` には決して到達しません。
`cloudfront.net` を登録しても、**一度もヒットしない**のです。

しかもホスト名は利用者ごとのランダムな文字列なので、個別に登録することもできません。
エラーは出ず、**ページが崩れる形でだけ表面化します**。

そこで「配下すべてに及ぶ」という印を付けたレコードだけを特別扱いします（ADR-0008）。
これを付けてよいのは**同梱の基盤ドメインだけ**です。
`blogspot.com` や `github.io` も同じ公開サフィックスですが、
第三者が中身を置けるサブドメインを取れるので付けてはいけません。

## 8. データの保存

SQLite という、1 つのファイルで完結するデータベースを使います。
サーバーを立てる必要がなく、Windows での配布が楽になります。

### テーブル

| テーブル | 中身 |
| --- | --- |
| `domain_records` | サイトの分類 |
| `domain_record_categories` | サイトと種類の対応 |
| `categories` | 種類の一覧 |
| `profiles` | 4 つのモードの設定 |
| `parent_overrides` | 許可リスト・拒否リスト |
| `emergency_blocks` | 緊急停止リスト（現状は空） |
| `access_decisions` | 判定の履歴 |
| `settings` | その他の設定 |

### 判定履歴の列は増やさない

`access_decisions` に保存してよいのは次の 7 列だけです。

```
timestamp / device_id / domain / category / decision / profile / rule_id
```

**ページの中身・検索語・Cookie の列は作りません。**
これは「入れないように気をつける」のではなく、
**テストで列の集合を固定してあります**。
うっかり列を足すと CI が落ちます。

将来 WFP など新しい層を足すときに、
勢いで情報を混ぜ込んでしまわないための防波堤です。

### 設定は必ず filter-core 経由で変える

データベースを直接書き換えると、**ポリシーの版数が上がりません**。
動いているサービスは 2 秒ごとに版数だけを見ていて、
変わっていれば読み直す仕組みになっています。

版数が上がらないと、サービスは古い設定のまま動き続けます。
「画面で許可したのに繋がらない」という、原因の分かりにくい形で出ます。

## 9. Windows 側のしくみ

### サービスとして常駐する

画面を閉じてもフィルターが動き続けるよう、Windows サービスとして登録します。
パソコンを起動すると自動的に始まります。

このとき注意している点がいくつかあります。

**準備ができてから「動いている」と報告する。**
起動から待ち受け開始までデータベースの準備に約 0.6 秒かかります。
先に「動いています」と報告すると、直後の問い合わせが
**まだ誰もいないポート**に届いて失敗します。

**受信エラーで待ち受けをやめない。**
Windows では、すでに閉じた相手に返事を送ると
こちらの次の受信が失敗します。問い合わせは常に別のプログラムから来るので、
これは日常的に起きます。ここで止めてしまうと、
相手が 1 つ先に消えただけで**フィルター全体が黙って停止します**。

**画面出力はファイルに書く。**
サービスとして起動されたプログラムには画面がありません。
`println!` で書いても、どこにも出ずに捨てられます。
失敗しても何も残らないので、ファイルに記録します。

この 2 つの不具合は、テストでは出ず、
**実際にサービスとして動かして初めて見つかりました**。

### DNS の設定を差し替える

パソコンの「DNS サーバー」設定を `127.0.0.1`（自分自身）に向けます。

このとき、**ネットワークの接続口ごとに個別に設定し、30 秒ごとに再適用します**。
VPN や USB テザリング、新しい Wi-Fi アダプタが後から現れても、
次の巡回で拾えるようにするためです。

元の設定は保存しておき、いつでも戻せます。
**この記録は上書きしません** — 2 回目の巡回で「iFilter に向いた状態」を
元の設定として記録してしまうと、二度と戻せなくなるからです。

### IP アドレスでの遮断（WFP）

DNS での遮断には抜け道があります。ブラウザの設定に

```
https://1.1.1.1/dns-query
```

と**数字で**書かれると、名前を調べる手順が起きません。
DNS プロキシに問い合わせが来ないので、名前による遮断は素通りします。

そこで Windows Filtering Platform（WFP）という仕組みで、
その接続先自体を塞ぎます。

- **ドライバは作りません。** ユーザーモードの API だけで実現でき、
  Windows SDK があればビルドできます
- **IPv4 と IPv6 の両方**に入れます。片方だけでは残った側で抜けられます
- **プロセスが終われば設定も消えます**（動的セッション）。
  残ってしまうと、フィルターを止めたのに通信が塞がったままになり、
  **保護者が復旧できません**

最後の点は重要な判断です。「遮断漏れ」より
「パソコンが繋がらなくなって原因も分からない」ほうが重い事故だと考えています。

## 10. 保護者向け画面のしくみ

Tauri という仕組みを使っています。**画面は Web の技術（React）で作り、
中身は Rust で動かす**構成です。

```
   React（見た目）  ←→  Rust（コマンド）  ←→  filter-core
```

### 画面には判定を書かない

React 側にも Rust 側にも、判定のロジックは書きません。
コマンドは `filter-core` の薄い包みです。
書いた瞬間に「画面では許可なのに実際は遮断」が起こりうる状態になります。

### 起動時に管理者権限を要求する

画面を開くときに Windows のパスワードを求めます。
子供のアカウントを「標準ユーザー」にしておけば、
保護者の資格情報なしには開けません。

暗証番号を別に用意する方式は採りませんでした。
覚えるものが増えず、Windows のしくみをそのまま使えるためです。

### 遮断記録のまとめ方

1 つのページは多数のサイトから部品を集めるので、
1 件ずつ許可させると運用が破綻します。

ところが **DNS には「どのページ由来か」の情報がありません**。
そこで時間の近さ（5 秒以内）でまとめた**推測**にしてあり、
画面でも「確実には分かりません」と伝えています。

推測でもまとめる価値が勝る、という判断です。

## 11. なぜこの作りにしたのか

主な設計判断とその理由です。詳しくは `docs/adr/` にあります。

| 決めたこと | 理由 |
| --- | --- |
| 判定を Core 層に閉じ込める | 2 か所に書くと必ずずれる。Android にも持っていける |
| 未知のサイトは既定で遮断 | 分類漏れが「素通り」ではなく「見られない」側に出る |
| HTTPS の中身を復号しない | 通信内容を見ずに済む方式を選ぶ。信頼の前提が変わる |
| DNS が第一段、WFP が第二段 | 実装コストが低い順。DNS だけで大半に効く |
| 判定順序を 9 段で固定 | 空の段を持つことで、後から機能を足しても順序が崩れない |
| DoH 対策を MVP に含める | 無いと「動いているように見えて素通り」になる |
| `doh` だけ保護者も解除できない | 1 件の許可が他のすべての設定を無効にするため |

## 12. 開発の進め方

### 検証コマンド

```bash
cargo build --workspace
cargo test --workspace
cargo fmt --all -- --check
cargo clippy --workspace --all-targets          # 警告ゼロが必須

# 判定部分が Android へ持っていけることの確認
cargo check -p policy-engine --target aarch64-linux-android
```

Android の確認は**リンクしないので NDK が無くても通ります**。
判定ロジックが Windows 固有のものに依存し始めたら、ここで落ちます。

### テスト

現在 296 件あります（Core と Windows で 273 件、画面で 23 件）。

| 種類 | 何を守るか |
| --- | --- |
| 段階ごとのテスト | 9 段それぞれが正しく動くか |
| 優先順位テスト | 各段が 1 つ上の段に負けるか |
| プロパティテスト | ランダムな入力を大量に試し、成り立つべき性質を確認 |
| 同梱データのテスト | 登録したドメインが**実際にヒットするか** |
| 列の固定テスト | 判定履歴に余計な列が増えていないか |

**同梱データのテスト**が特徴的です。単に「登録した」だけでは
CDN のように一度もヒットしない場合があるため、
**ブラウザが実際に引くホスト名**で照合を確かめています。

### CI

GitHub Actions で、`iFilter/` に変更があると自動的に実行されます。
Windows 固有の部分があるため Windows 上で動かします（約 9 分）。

## 13. 用語集

| 用語 | 意味 |
| --- | --- |
| **DNS** | サイト名から住所（IP アドレス）を調べる仕組み。電話帳にあたる |
| **DoH** | DNS の問い合わせを暗号化して特定の事業者に直接送る仕組み。iFilter を迂回できてしまう |
| **NXDOMAIN** | 「そのサイトはありません」という DNS の答え。遮断に使う |
| **eTLD+1** | 「登録可能な一番短いドメイン名」。`example.co.jp` など |
| **公開サフィックス** | その下に誰でも登録できる部分。`co.jp` `com` など |
| **CDN** | 画像やプログラムを高速に配る仕組み。1 つのページが多数を使う |
| **WFP** | Windows の通信制御の仕組み。IP アドレスで接続を止められる |
| **ALE レイヤ** | WFP の中で「これから接続する」場面を扱う層。パケットの中身は見ない |
| **クレート** | Rust のコードのまとまり。1 つの部品にあたる |
| **プロファイル** | 4 つのモード（はじめて／すこし慣れた／標準／中高生）のこと |
| **Verdict** | 判定の結果。判断・理由・根拠のルール・経過を含む |
| **Trace** | 9 段階のどこで結論が出たかの記録。画面で理由を説明するために使う |
