# ADR-0010: WFP はユーザーモードの ALE レイヤで、既知 DoH プロバイダの IP だけを塞ぐ

- 状態: 採用（2026-08-16 の Step 11 で検証・同日承認）
- 日付: 2026-08-16

## 文脈

ADR-0007 で DoH 対策を MVP に含めると決め、Step 6.5 と Step 8 で
**ドメイン名による遮断**を実装した。既知プロバイダを `doh` カテゴリに入れ、
DNS プロキシが NXDOMAIN を返す。ブラウザ側のポリシー（`DnsOverHttpsMode = off`）
も併用している。

しかしこれには穴がある。ブラウザの DoH 設定は URL を直接指定でき、

```
https://1.1.1.1/dns-query
```

と数字で書かれると**ブラウザは名前解決を一切行わない**。DNS プロキシに問い合わせが
来ないので、ドメイン名による遮断は素通りになる。これは ADR-0004 が
「第二段で IP 直打ちと DoH の IP アクセスを塞ぐ」とした対象そのものである。

## 検証（Step 11・実測）

方式を決める前に、ユーザーモード WFP が本当に使えるかを確かめた。
`FwpmEngineOpen0` / `FwpmFilterAdd0` を Rust（`windows` crate 0.62）から呼び、
`1.1.1.1:443` への TCP 接続が前後でどうなるかを見た。

| 確かめたこと | 結果 |
| --- | --- |
| WDK なし・Windows SDK だけでビルドできるか | できた |
| 非管理者でエンジンを開けるか | **開けた** |
| 非管理者でフィルタを追加できるか | できない（`ERROR_ACCESS_DENIED`） |
| ALE レイヤのフィルタが実際に効くか | **効いた**（接続可 → 接続不可） |
| プロセス終了でフィルタが消えるか | **消えた**（接続不可 → 接続可） |

ARCHITECTURE.md §1 の「ユーザーモード WFP で足りる見込み」が実測で裏づけられた。
必要な feature は `Win32_NetworkManagement_WindowsFilteringPlatform` に加えて
`Win32_Security` と `Win32_System_Rpc`（`FWPM_SESSION0` と `FwpmEngineOpen0` が
これらに依存している）。

## 決定

### 1. ユーザーモード WFP の ALE レイヤを使う

`FWPM_LAYER_ALE_AUTH_CONNECT_V4` / `_V6`。「これから外向きに接続する」ところで
呼ばれる層で、パケット本体を触らないためカーネル callout ドライバが要らない。
IPv6 も必ず対象にする。主要プロバイダはどこも IPv6 を持っており、
v4 だけ塞ぐと**そのまま v6 で抜けられる**。

### 2. 動的セッションを使う（fail-open）

`FWPM_SESSION_FLAG_DYNAMIC`。プロセスが死ねばフィルタも消える。

静的に登録すると、フィルターが異常終了したときに**通信が塞がったまま残り、
保護者が復旧できない**。子供の PC がネットに繋がらなくなり、しかも原因が
見えない状態は、遮断漏れより重い事故になる。

DNS 層が「サービス終了時に DNS 設定を必ず元へ戻す」（Step 7）としたのと同じ判断。
素通りの危険は、UI が稼働状態を明示することと、SCM の失敗時再起動で受ける。

### 3. 塞ぐのは既知 DoH プロバイダの IP だけ

同梱データの `doh` カテゴリに対応する IP を列挙し、その宛先への接続を塞ぐ。
ポートは絞らない。対象は DNS 提供専用のアドレスなので、全ポート塞いでも
巻き添えが起きにくい。

**IP はハードコードする。** 起動時に名前解決して求めることはできない——
その名前は iFilter 自身が BLOCK している。

**載せてよいのは DNS 提供専用のアドレスだけ。** 実測したところ
`cloudflare-dns.com` は `1.1.1.1` ではなく `104.16.249.249`（Cloudflare の
**共有 CDN レンジ**）に解決された。無関係な顧客サイトが多数同居しているので、
これを塞ぐと「なぜか一部のサイトだけ見られない」を作り込むことになる。
`dns.nextdns.io` も解決先が地域ごとに変わるため入れない。

どちらもドメイン名では遮断されるので**無防備にはならない**。数字で直接
指定された場合だけが抜ける。混入は `domain-model` のテストが機械的に止める。

### 4. `unsafe` は `windows/wfp` crate に閉じ込める

既存の Windows 側 crate は `windows-registry` / `windows-service` という
安全なラッパーを使い `unsafe` を書かずに済ませてきたが、WFP に同等のものは無い。
生の Win32 API を呼ぶ `unsafe` はこの crate の内側だけに置き、外へは安全な
関数だけを出す。判定は一切持たず、`filter-core` から受け取った結果を実現するだけ
（ADR-0001）。

## 却下した案

### DNS 由来 IP の許可制

DNS プロキシが ALLOW した応答の IP を記録し、覚えのない IP への接続を全部塞ぐ。
IP 直打ちも未知の DoH プロバイダもまとめて塞げる、最も強い方式。

採らない理由は副作用の重さ。PC の全通信が対象になるため、LAN のプリンタや NAS、
IP を直接使うアプリ（一部のゲーム、機器の検出処理）が動かなくなる。しかも
症状は「特定のアプリだけ、原因不明で繋がらない」という形で出る。**保護者が
iFilter のせいだと気づけない**まま、PC が壊れたように見える。

実装も軽くない。DNS プロキシは現在「応答を解析せずそのまま転送する」設計
（Step 8。新しいレコード種別が出ても壊れないため）で、応答の解析と TTL 管理を
足すことになる。

対象は小学生であり、現実に起きるのは「ブラウザの設定画面で DoH を有効にする」
であって「IP を調べて直接打ち込む」ではない。**起きやすい経路を確実に塞ぐほうが、
起きにくい経路まで塞いで PC を不安定にするより価値が高い。**

指示書 21 の「最初から複雑なものを作らない」、ROADMAP Step 12 の
「最小限に絞る」とも一致する。

## 結果

- **塞げるもの**: ブラウザの DoH 設定で既知プロバイダを選ぶ／URL に IP を直接
  書く。ドメイン名・ブラウザポリシーと合わせて三重になる
- **塞げないもの**: リストに無いプロバイダ、自前で立てた DoH サーバー、
  一般サイトへの IP 直打ち、VPN
- IP が変わったら追随が要る。ドメイン名側の遮断が残るので、
  変わっても**無防備にはならない**（数字での指定だけが抜ける）
- フィルタ操作には管理者権限が要る。サービス（LocalSystem）から行う。
  UI は起動時に昇格済みなので、そこからの操作も通る
- 検証で使った PoC はリポジトリに残さない。Step 12 で `windows/wfp` として
  本実装した

## 実装後の追記（2026-08-16・Step 12）

`windows/wfp` として実装し、管理者権限で通しの確認をした。同梱の 24 件を塞ぎ、
`1.1.1.1` `8.8.8.8` への接続が「できる → できない → できる」と推移することを
確認している（`cargo run -p ifilter-wfp --example block_doh`）。

サービスへの適用は `--enforce-dns` に連動させた。フラグを増やすと「どれを付ければ
守られるのか」が分かりにくくなるため。**WFP の失敗では待ち受けを止めない** —
ドメイン名の遮断は働いており、サービスごと落とすと DNS フィルタまで失う。
黙って進まないよう `service.log` に必ず残す。
